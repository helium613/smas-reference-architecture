# ハブの法則と、SMASの位置づけの再定義

**ステータス: 作業ノート(戦略・位置づけの検討)。`docs/DECISIONS.md`が扱う実装上の設計判断ではなく、プロジェクトの立ち位置そのものについての整理。競合調査の事実部分は検証済み、法則とその含意は「反例の少ない傾向」として扱い、定理としては扱わない。**

2026-07-25の議論の記録。発端は「自分のプロジェクトに需要があるのか」という疑念で、競合調査 → 批判的評価 → 「ハブの法則」の抽出 → SMASの位置づけの再定義、という順で進んだ。結論を先に書くと、**SMASの実質的な目標は「ハブ不在の協調を実現すること」ではなく「ハブが運用する仕組みの耐戦略性を検証可能にすること」である**、という読み替えに至った。

---

## 1. 競合調査(検証済み)

エージェント基盤系の5リポジトリを調査した。

| プロジェクト | 実体 | ②誘因構造 | ⑤検証 |
|---|---|---|---|
| naptha-sdk / naptha-node | モジュール実行基盤・P2Pホスティング・ストレージ | 言及なし | 言及なし |
| Open Autonomy (Olas) | オフチェーンMASがオンチェーン機能を拡張 | ステーキング設計あり(定性的) | 言及なし |
| agents-aea (Fetch.ai) | 「自律経済エージェント」フレームワーク | Contract Net型の交渉実装あり | 言及なし |
| uAgents (Fetch.ai) | 軽量Pythonエージェントライブラリ | 言及なし | 言及なし |

**結論: 競合度は低い。** 5つとも①環境層(通信・ホスティング)+④実行主体層(SDK)の「配線」を作るプロジェクトで、②誘因構造層(誘因整合性・耐戦略性)にも⑤検証層(形式検証)にも実質的な言及がない。SMASがCLAUDE.md 3章で明示的にスコープ外としている領域(P2P通信・ノードホスティング・ブロックチェーン統合)が、この5つの本体。層で住み分いている。

### 深堀り(当たりをつけた2つ)

「Fetch.aiとOlasは奥に踏み込んだ誘因設計があるのでは」という仮説で追加調査したが、**当たりは外れた**。

- **Fetch.ai**: 開発者ドキュメント(`contract.md`)はAPI利用ガイドに終始。自社の学術論文("Fetch.ai: An Architecture for Modern Multi-Agent Systems", arXiv:2510.18699)は、**「古典的プロトコルには数学的な公平性保証があった」と歴史的に言及するのみで、自分たちの実装がその性質を満たすかは形式化していない**。これはSMASが埋めようとしているギャップそのもの——競合というより適用対象に見える。
- **Olas**: 開発者ドキュメントは定性的説明のみで詳細はホワイトペーパーに委譲。**そのホワイトペーパー(`Autonolas_Tokenomics_Core_Technical_Document.pdf`)・監査レポートともにパスワード保護で開けず、内容を確認できなかった**(調査の限界として明記)。確認できた実装上の性質として、**スラッシング(不正への直接的な経済的ペナルティ)は実装されておらず**、KPI未達時は報酬を与えないだけ。

## 2. 批判的評価(この議論で最も重い部分)

「需要があるのか」という疑念に対し、率直な批判を求めた結果。以下は反論可能な指摘として記録する(反論できたものは反論を併記)。

1. **「先駆的だから不安は当然」という枠組み自体が危険**。「早すぎる」と「需要がない」は観測される証拠が同一(誰もやっていない・反応が薄い)なので、この説明は反証不可能。区別には外から別の証拠を持ってくるしかない。
2. **2つの別プロジェクトが1つに見えている**。主張A(協調メカニズムの誘因整合性の検証)と主張B(委任チェーンの権限合成リスク検出)は需要プロファイルが違い、**Bの方が明確に需要がある**(CIEM市場が実在、role chaining攻撃が実報告、A2A仕様の穴を確認済み)。後継3プロジェクトのうち2つがBに属することが、顕示選好としてそれを示している。
3. **自分の実験結果が主張Aの前提を部分的に崩している**。D-47・D-54で確認した通り、中立的な指示のLLMは埋葬戦術にも信用枠内過大申告にも自発的に到達しなかった。**今日のLLMエージェントはSMASが想定する戦略的主体ではない**。現実の障害モードは幻覚・プロンプトインジェクション・ツール誤りであって、私的情報を持つ主体の意図的な虚偽申告ではない。主張Aに需要が生まれるのは(a)意図的に操作的なエージェントが作られる、(b)最適化圧力で戦略的行動が創発する、のどちらか——D-45(最適化ベースが独立に同じ穴に到達)は(b)の萌芽的証拠だが、まだ1ケース。
4. **先行研究の再発明リスクはパターンとして繰り返しうる**。taxonomyの一件(`notes/delegation_chain_taxonomy.md`)は単発の失敗ではない。委任・アクセス制御の形式化は1976年から50年の蓄積があり、メカニズムデザイン側もCOMSOCが同種の作業を続けている。
5. **検証層の実力は看板より薄い**。DisCoPyは型接続の事後チェックのみ(CLAUDE.md自身が明記)、5大指標の②収束性は6ケース中5ケースでN/A、④資源コストは実質的に実行時間。実質的な検証力はモンテカルロとGambitで、これは標準的な道具。
6. **顧客が特定されていない**。6ケース・25評価観点・可視化を作って、「誰が使うのか」がどこにも書かれていない。D-12の自己診断(ドキュメント量が実装量を一桁上回る)の根っこは、作る対象が決まっていないことかもしれない。

**反論できた点**: 判断の質(実装ミスと分かった「発見」を撤回する、未検証を未検証と書く、記事を保留する)は希少で、多くのプロジェクトはこれができない。ただし**これは個人の能力の証拠であって市場の証拠ではない**——混同しないことが重要。

## 3. ハブの法則(この議論の分析的な核)

### 定式化

> **分散・連合設計は「配管の層」では生き残り、「調整の層」ではハブに負ける。**

### 支持する証拠

| 事例 | 配管の層 | 調整の層 |
|---|---|---|
| Git / GitHub | Gitの分散データモデルは完勝 | 社会的なやり取りはGitHubに集中 |
| メール | SMTP連合は存続 | 実運用はGmail/Outlookの寡占 |
| PKI | 構造上は連合 | 実態は少数CA+ブラウザのルートプログラム |
| XMPP | — | 体験の層で戦って WhatsApp/Slack に敗北 |
| Web3 / DAO | ステーブルコイン・L2など「退屈な配管」は存続 | 「あらゆる組織をDAOに」の思想は崩壊、多くが寡頭制化 |
| **ブロックチェーン(最強の試金石)** | — | **調整をハブなしでやると明示的に設計されたのに、マイニングプール・取引所・L2シーケンサに集中した** |

### 留保

反例もある(BGPは調整寄りでありながら階層付きの連合を保っている)。**傾向であって定理ではない**——設計判断の重みづけには使うが、証明の代わりにはしない。

## 4. SMASへの含意

### (1) ③集約層こそが「調整の層」

`run_mechanism()`は全員の申告を集めて1つの結果を出す関数であり、定義からして調整。誰かが実行しなければならない。法則が正しいなら、**②③はハブに収斂する**。①環境層(痕跡の保管)と④主体決定層は配管の層で、分散のまま残れる。

### (2) 6ケースが層で二分される

- **ケース1〜4(VCG・信用枠・投票・Liquid Democracy)**: すべて「全員の申告を集めて1つの答えを出す」構造 → **調整の層、ハブが立つ**
- **ケース5・6(IAM委任・予算委任)**: 基本の安全性チェックが各ノードのローカル状態だけで完結する(a2a-gate-chain D-07で確認済み)。集約が要らない → **配管の層、分散が成立する**

**§2-2で観察した「主張AとBの分裂」には、層の違いという構造的な理由があった。** 後継プロジェクトが両方ケース5・6から出ているのは偶然ではなく、分散設計が構造的に成立する唯一の場所だから。

### (3) 「外生的に仮定する」リストの読み替え

CLAUDE.md 3章が外生的に保証されると仮定しているもの——支払いの執行、同期ラウンド進行の権威、参加者の同一性——は、現状「中央性の残余」として記述されている。法則が正しいなら、これらは**後で埋まる穴ではなく、ハブが立つ場所を正確に予言したリスト**として読むべき。実際、支払いの執行とラウンドの進行は、まさに調整の層の仕事。

### (4) 調整の層での逃げ道は「分散」ではなく「検証可能性」

調整の層でハブに正面から挑むのは負け筋(XMPPの失敗)。歴史的なもう1つの道は、**ハブが計算することは認めた上で、その計算を誰でも検証できるようにする**こと(Certificate Transparency、ブロックチェーンの公開検証)。

そしてSMASは既にその形で作られている——②誘因構造エンジンは純関数、入力は①環境層の公開痕跡、⑤検証層は実行パイプラインの外から監査する。

## 5. 位置づけの再定義(この議論の結論)

> **SMASの実質的な目標は「ハブ不在の協調」ではなく、「ハブが運用する仕組みの耐戦略性を検証可能にすること」。**

この読み替えは市場を狭めず、むしろ広げる。調整の層のハブ(広告オークション、マーケットプレイス、配分システム)は実在していて資金もある。「あなたの分散システムを検証する」より「あなたが運用している仕組みが本当に耐戦略的か検証する」の方が、顧客がはっきりする。

なおCLAUDE.md 2章 原則1「中央の執行者を作らない」は、アーキテクチャ上の原則(フレームワークにデータの実体を持たせない)としては生き残る——「誰が計算するか」ではなく「誰かが一方的に運命を決める構造をコードに埋め込まない」の話であるため。ただし**対外的な一言定義で「非中央集権」を前面に出す書き方は、この法則と整合しない**ので、見直しの候補。

## 6. 派生した判断

### 分散ドメインに賭ける理由(思想ではなく構造)

「信頼ドメイン内のA2Aの方が需要があるのでは」という疑念は見立てとして正しい。ただし**ドメイン内は問題が既に定義されている**(それは認可であり、OpenFGA・SpiceDB・Cedarが競合し、答えの形も分かっている)。そこで勝つのに要るのは資金と実装速度で、この プロジェクトの強み(概念を精密に切り分ける力、撤回する誠実さ、体系化)は換金されない。

また、**元々の動機はパーソナルエージェント基盤**だった。そこでは分散は思想ではなく定義になる——あなたのために動くエージェントの権限をプラットフォームが管理しているなら、それはもうあなたのエージェントではない。CLAUDE.md 原則1の出所もここ。

分散設計への動機には美意識の成分も混ざっているが、**戦略的な理由(パーソナルエージェントには構造的に中央が置けない)と美意識は分けて持つ**。前者は検証可能な主張、後者は燃料であって判断の根拠ではない。

### プロジェクト間の優先順位

- **a2a-gate-chain**: 既にシステム実装として実体がある(ゲート・チェーン伝播・ext_authz・OPA/Envoy/Cloud Run配線・ビジュアルデモ・テスト、D-20まで)。**完走させる**。新規にプロジェクトを後発させる必要はなく、これがそのシステム実装。
- **smas-confused-deputy**: 実装ゼロ。本来の役割(ドメインの物語+可視化)はa2a側の`demo/visual/gate-chain.html`が果たし始めている。**並行実装はせず、ピッチ用の物語資産に降格または吸収**。
- **smas-self-enforcing-scm**: 主張A側で需要プロファイルが最も弱く、実装ゼロ。**明示的に凍結**(「保留」ではなく凍結と書いて判断を蒸し返さない)。

### OpenFGAとの関係についての自己評価の訂正

議論の中で「委任合成検出ロジックはOpenFGAでもできている」という自己評価が出たが、**これは自分がa2a-gate-chain D-20で出した結論より悲観的**。D-20は、ReBACは数値の集約(MAX/SUM)や順序比較を持たず、tierの到達可能性は表現できても「MAX vs 宣言上限」の比較は外付けが要り、予算(消費的・保存則)は原理的に表現不能、と結論している。OpenFGAがくれるのは到達可能性までで、**昇格判定はくれない**。

## 7. 未解決・留保

- **可視性と成功指標の不整合(最重要)**: 「製品化ではなく概念提唱」という位置づけなら、世界に吸収されることは脅威ではなく成功条件。ただしそれが成り立つのは仕事が見える状態にあるときだけで、現状はリポジトリ非公開・記事保留・taxonomy未公開。**成功の定義(伝播・影響)と現在の行動(非公開・慎重)が食い違っている。**
- **「早すぎる」か「需要がない」かの判別**: 外から証拠を持ってくるしかない。ハッカソンが最初のテスト。confused deputy検出は今日の問題なので、反応が薄ければ「早すぎる」の言い訳が使えない=有意な情報になる。
- **Macaroonsの採用実績**: 2014年からある優雅な原理が11年経ってもニッチ(Tailscale・Fly.io等)。需要が薄い証拠とも、採用の谷を誰も越えていない証拠とも読める。
- **Olasのホワイトペーパー本体**: パスワード保護で未確認。重要な局面(資金調達・正式な比較)で使うなら人力での入手が必要だが、優先度は低い。
- **ハブモデルでも生き残る根拠**: 組織が内部の委任構造を出さない理由は、信頼の欠如だけでなく競争上のセンシティブさと高カーディナリティ。これは「信頼が生まれれば解消する」タイプの制約ではないので比較的丈夫、という見立て(未検証)。
